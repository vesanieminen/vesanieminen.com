Does promptfoo fit agentic-dx-improvement?

An evaluation of whether promptfoo belongs in the Vaadin agentic-DX benchmark harness.

Prepared 2026-06-08 · Goal under consideration: benchmark how well different coding agents build Vaadin apps, and track whether it gets easier or harder over time.

Verdict up front

Partial fit — and the part that fits is not the part you most care about.

Promptfoo is an excellent fit as a thin orchestration + scoreboard + CI-gate layer wrapped around your existing run_task.sh / verify_task.sh. It is a poor fit as the grader (your grading is agentic and browser-driven; promptfoo's llm-rubric is single-shot text grading) and it has no concept of your primary signal (the behavioural trace, per CONTEXT.md).

The specific thing you named — "is it getting easier or harder day by day" — is also not promptfoo OSS's strong suit. It does pairwise eval comparison well; longitudinal trend charts are an Enterprise/cloud feature.

Bottom line: don't abandon the idea. Adopt it for the matrix / scoreboard / CI gate, keep your custom solve + verify + trace pieces, and don't expect it to be your trend dashboard.

How the two models line up

Promptfoo's universe is prompts × providers × tests → run each cell → score with assert → store results → compare in a web UI / gate in CI. Its unit of work is one provider call (an LLM call) → text output → assertions.

Your universe is (agent × stack × problem) → a multi-minute agentic Docker run → a filesystem tree + logs + cost summary → graded by a second agentic Docker run that boots the app and drives Playwright against a rubric. Four signals come out, the behavioural trace being primary.

What you'd genuinely gain

  1. Declarative matrix instead of bash loops. providers: [claude, codex] × tests: [basic_form, basic_layout, md_ui_spec] replaces hand-rolled loops, with built-in concurrency and a results store.
  2. A real comparison UI for free. promptfoo view gives you the side-by-side matrix (agent × problem, with cost/score columns) you'd otherwise hand-build.
  3. Cost / tokens become first-class. Your custom provider returns cost + tokenUsage from summary.txt; promptfoo aggregates and charts them. Directly serves your "cost & speed" floor-constraint signal.
  4. CI gate + cron. The GitHub Action + non-zero exit on regression gives you the daily-run trigger essentially for free.
  5. Variance handling. repeat: N runs each cell N times and averages — important because a coding agent is highly stochastic and one run per cell is noisy.
  6. The base-prompt A/B loop, formalized. One of your three stated iteration loops is "tweak base_prompt_<stack>.md and re-run." That maps exactly onto promptfoo's core competency: put the base prompt in as the prompt and let promptfoo run the variation matrix. This is the single most idiomatic alignment.

Where it fits poorly (the honest part)

1. Your grader is agentic; promptfoo's is not

llm-rubric / g-eval send output text + rubric to an LLM in one shot. Your rubric requires booting the app in production mode, resizing to six viewports, checking for horizontal scrollbars, instantiating the form inside a dialog, and reading source for setRequiredIndicatorVisible. No model-graded assertion can do that. You keep verify_task.sh — it's your crown jewel and nothing off-the-shelf replaces it.

2. Your primary signal is invisible to promptfoo

CONTEXT.md is explicit: the behavioural trace ("which skills fired, where it backtracked, API archaeology") is the deciding voice, above the rubric score. Promptfoo has no model for this. You can stuff trace-derived numbers (archeology-seconds, MCP-lookup count) into metadata as metrics, but promptfoo shows them as columns of numbers — it won't give you the narrative your scripts produce, and it won't derive them. Promptfoo would systematically under-serve the signal you steer on most.

3. "Output" isn't text here

The artifact is a filesystem tree + a running server. Not fatal — the provider returns a handle (run-dir path) as output and the real evaluation lives in metadata/metrics — but you're using promptfoo against its grain.

4. The two-stage solve→verify pipeline doesn't match the single-call model

Promptfoo thinks "one provider call → assert." You have two agentic runs. You can shoehorn (run verify inside the provider and return the score; or wrap verify as a custom python assertion), but neither is the path promptfoo is designed around.

5. The variables you iterate on most are outside promptfoo's provenance

You tune the skeleton, the skills submodule, and MCP behaviour — all of which live in the Docker image + the agent-skills submodule, invisible to promptfoo. It will record the prompt + provider config and think two runs are "the same" when the skeleton or skills changed underneath. Its caching and history comparisons are blind to your most important knobs unless you manually inject git rev-parse of the submodule, the image digest, etc. into provider metadata.

6. "Easier day by day" is a trend question; OSS promptfoo answers diff questions

It stores every eval with a timestamp and lets you compare two named evals. A 90-day trend line of "rubric score for basic_form on claude" is not a built-in OSS view (that's promptfoo cloud/Enterprise). For your stated goal you'd still export the metrics to your own time-series/CSV + a chart. Promptfoo gives you the per-run datapoints and a scoreboard, not the trend.

If you adopt it: the idiomatic shape

Keep run_task.sh and verify_task.sh exactly as they are. Add promptfoo as a layer on top.

# promptfooconfig.yaml
prompts:
  # The base prompt IS the thing under test — the idiomatic A/B knob.
  - file://problems/base_prompt_vaadin.md
  # - file://problems/base_prompt_vaadin.variantB.md

providers:
  - id: file://providers/agent.js   # custom JS provider, see below
    label: claude
    config: { agent: claude }
  - id: file://providers/agent.js
    label: codex
    config: { agent: codex }

tests:
  - vars: { problem: basic_form,   stack: vaadin }
  - vars: { problem: basic_layout, stack: vaadin }
  - vars: { problem: md_ui_spec,   stack: vaadin }

defaultTest:
  assert:
    - type: javascript            # cheap deterministic gate
      value: output.metadata.build === 'pass'
    - type: javascript            # route verify-result.json in as the real score
      value: output.metadata.rubricScore >= 0.8
      metric: rubric
  options:
    # Caching MUST be off — every benchmark run is fresh.
    # Timeout must be generous — these runs take minutes.

The custom provider (providers/agent.js) is the whole integration. It:

  • shells out to run_task.sh <config.agent> <vars.stack> <vars.problem> (feeding in the base prompt),
  • optionally runs verify_task.sh too,
  • parses summary.txt → returns { cost, tokenUsage } (first-class),
  • parses verify-result.json → returns per-section scores as metadata metrics,
  • returns trace numbers from agent_timing.py / agent_archeology.py as metadata,
  • returns the run-dir path as output.

Then promptfoo's matrix shows agent × problem, with columns for rubric score, cost, time, and your trace metrics — a legitimately nice scoreboard.

Run discipline that's mandatory here

  • --no-cache (or cache: false) — every benchmark run must be fresh.
  • Low --max-concurrency — each cell is a heavyweight Docker + Maven + Playwright run; 2–3 in parallel, not 10.
  • Generous per-provider timeout, reconciled with your existing summary.txt watchdog so promptfoo's timeout doesn't kill a healthy run.
  • repeat: 3+ to fight agent stochasticity.

Footgun checklist

  • Caching is on by default → would silently return stale results for a benchmark. Disable it. Easy to forget; corrupts your data if you do.
  • Cost blow-up. matrix = agents × problems × repeat × days. Each cell is a multi-minute, real-dollar agent run plus a multi-minute agentic verify. This grows fast; budget it before wiring a daily cron.
  • Concurrency. Docker + JDK + Playwright/Chromium is RAM/CPU-heavy. Promptfoo's default concurrency will thrash your machine. Cap it.
  • Timeouts. Multi-minute runs vs promptfoo's default provider timeout. Must be raised and reconciled with your watchdog.
  • Provenance / reproducibility. For "easier over time" to mean anything, pin: full model IDs (use full IDs, not floating aliases), skeleton version, agent-skills submodule SHA, Docker image digest. Promptfoo won't capture these unless you inject them into metadata.
  • The remote-MCP confound. Your skills point at https://mcp.vaadin.com/docs, a remote server that changes outside your control. That is simultaneously a thing you want to measure (better docs → easier for the agent) and a confound (a score drop on a fixed problem might be the MCP server regressing, not the agent). Nothing can disambiguate this without snapshotting MCP responses — you already have mcp_probe.py; consider logging its output per run as a provenance record.

Alternatives to weigh

  • Do nothing / extend what you have. You've already built the hard, domain-specific parts: matrix runner, cost parsing, agentic grader, trace analysis. Promptfoo would replace only the thin glue (loops) and add a UI/CI. A ~150-line aggregator that walks results/**/verify-result.json + summary.txt into a CSV + chart would directly serve your "daily trend" goal with zero new dependency and full fidelity to your four signals — including the behavioural trace promptfoo can't represent.
  • Promptfoo as scoreboard only, your scripts as engine. The middle path described above — best ratio of value to shoehorning.
  • General agent-eval harnesses (Inspect, SWE-bench-style runners, OpenAI evals): all share promptfoo's blind spot — none grade a live browser-rendered UI against a visual rubric. Your verify_task.sh is genuinely more specialized than anything off-the-shelf. Keep it whatever you decide.

Recommendation

It depends on which pain you're actually trying to relieve. The honest answer is conditional:

If your pain is orchestration

Adopt promptfoo

If the felt pain is "bash loops are unwieldy and I want a comparison UI + CI gate + cost tracking" → adopt it as the thin orchestration layer (custom provider wrapping run_task.sh, verify routed in as metadata, --no-cache, low concurrency, repeat). Low risk, real convenience, and it formalizes your base-prompt A/B loop.

If your pain is the trend

Build in-house instead

If the felt pain is "I want to track the behavioural trace and a true day-by-day difficulty trend" → promptfoo is the wrong primary tool. You'd fight it on both your primary signal and the trend view. A small in-house aggregator over results/ (or promptfoo Enterprise) serves that better. Promptfoo can still ride along as a secondary scoreboard.

It's not "abandon the idea" — it's "use it for the matrix / scoreboard / CI, not for grading or trace, and don't expect it to be your trend dashboard."

Suggested next step

Pick one small, self-contained spike:

  • (a) Prototype the custom JS provider + promptfooconfig.yaml, run the matrix once, and look at the UI.
  • (b) Sketch the lightweight in-house aggregator + trend chart over results/ instead.

Either answers the open question — "is the orchestration convenience worth a new dependency, or do I just want the trend?" — in an afternoon.
