1. Production-relevant bug fixes

These are the items most likely to bite a customer app you're maintaining today.

URLs with + in the path no longer throw InvalidLocationException

merged cherry-picked to 24.10 24.10.x

Re-encodes the location query parameter on the init request so a literal + in the path (e.g. /+/dashboard) survives the servlet container's query-parameter decoding. Previously the + was decoded as a space and Flow threw InvalidLocationException: Relative path cannot start with /.

The regression was introduced in #22791 to preserve %2F in wildcard parameters, but double-encoding handles that case correctly. If you have a workaround in a customer app (URL rewriting, route alias, etc.), you can remove it once the 24.10 patch is out.

Shared Signal reads stale value during concurrent UIDL requests

merged main

When a shared signal is updated concurrently with an in-flight UIDL request, effects associated with that UI would run against the request's repeatable-read transaction and see the cached old value, silently missing the update. The session-scoped transaction is now cleared before pending access tasks run, so effects see fresh values.

Originated from a customer Slack thread. If you use server-side Signals shared across UIs (cross-tab notifications, multi-user dashboards) this is the kind of subtle staleness that's hard to reproduce locally.

False infinite-loop exception on cached Signal self-update

merged main

An effect reading from a cached signal whose value is stale would trigger a recompute + submit(), which then notified the still-active effect — and was wrongly flagged as an infinite loop. That's now treated as lazy evaluation, not a loop.

If you've used cached signals and seen spurious "infinite loop detected" exceptions in dev, this is the fix. No more try/catch workarounds.

2. New Action / Trigger framework

A declarative server-side API for binding browser gestures (click, key, resize, …) to outcomes that involve browser-only APIs (clipboard, fullscreen, downloads, popups). The pattern replaces hand-rolled executeJs snippets with typed Java actions whose success/error payloads come back to the UI thread automatically.

Status: primitives and the first three actions are merged on main; several concrete actions are open PRs. Nothing here is in a released version yet — but if you're maintaining customer code that already does navigator.clipboard.writeText(...) through executeJs, it's worth tracking.

Foundation: PromiseAction<T>, CopyTextToClipboardAction, RequestFullscreenAction

merged main

PromiseAction<T> is the generic primitive for any gesture-bound browser API that returns a promise. Subclasses override the JS expression; the base wires success/error back to the UI thread, with Jackson-decoded payload. 

// Future shape (main, not yet released)
button.addClickListener(e -> { /* server work */ });
button.addTrigger(new CopyTextToClipboardAction(() -> user.getEmail()));

Replaces the awkward "build a JS blob + register a return channel" recipe.

Read from clipboard: ReadFromClipboardAction + JsBuilder.callback primitive

merged main

Returns a ClipboardPayload(String text, String html) from navigator.clipboard.read(). Also adds the generic JsBuilder.callback(Class<T>, Consumer<T>) primitive that lets any custom action route a typed payload from client JS to the server.

First action that decodes a structured payload, not just success/failure. The callback primitive is what you'd reach for if you build your own action.

Open: more concrete actions

open PRs main
  • DownloadAction — static URL, DownloadHandler, or client-resolved Input<String>. Synthesises an <a download> click inside the user gesture.
  • OpenInNewTabAction — window.open with noopener,noreferrer by default. Survives popup-blocker rules because it runs inside a real user gesture.
  • CallbackAction<T> + SetSignalAction — push any client-side value back into server state, or directly into a Signal.
  • SizeTrigger + ElementResize.ts — fires on element resize via ResizeObserver; pair with SetSignalAction for a server-side sizeSignal().
  • SignalInput<T> — use a server-side Signal as the value source of an action without first projecting it onto a DOM property.

Customer code that today does el.executeJs("window.open($0, '_blank')", url), a hand-rolled ResizeObserver attach, or "click an invisible <a> to trigger a download" will get cleaner equivalents.

3. Smaller API improvements you'll actually use

Named parameters for executeJs

open main

Today:

element.executeJs("doSomething($0, $1)", foo, bar);

Soon:

element.executeJs("doSomething(foo, bar)")
       .withParameter("foo", foo)
       .withParameter("bar", bar);

Positional $0/$1 keep working. The withParameter mechanism is purely server-side: it prepends let foo=$N; to the expression. Same helper exists on JsFunction. callJsFunction deliberately stays unchanged. Big readability win for long snippets.

Virtual-aware component tree traversal helpers

open main

ComponentUtil.getAllChildren(component) and ComponentUtil.streamDescendants(component) — both include virtual children (slotted helpers like addToFooter, overlays attached to the UI, the client-side routing wrapper).

If you've ever reached into VirtualChildrenList (or wondered why getChildren() doesn't see the dialog you just opened) this is the supported replacement. Most customer codebases have at least one tree-walker that this simplifies.

NativeLabel.setFor() auto-generates IDs

open behavior change main

setFor(Component) now defers ID resolution to beforeClientResponse and auto-generates one if the target doesn't have an ID. You no longer have to call setId(...) manually on labelled inputs.

Tagged feat!: in commit history — if any customer code relies on the immediate NoSuchElementException-style behavior of the previous implementation, that contract changes. In practice, most usages get cleaner.
